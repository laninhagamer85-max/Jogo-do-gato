## Verified from official provider documentation

- **Server sessions:** Firebase Admin exchanges a freshly signed-in Firebase ID token for a server session cookie. Firebase recommends checking `auth_time` (the example uses a five-minute maximum) and protecting the exchange endpoint against CSRF. Session-cookie verification supports a revocation check. We use an HttpOnly, Secure, host-only cookie and a separate same-origin CSRF token; the app will refuse to issue a session if the provider ID token is stale, unverified, unsupported, revoked, or does not satisfy the role's MFA requirement.
  - https://firebase.google.com/docs/auth/admin/manage-cookies
- **TOTP MFA:** TOTP MFA requires Firebase Authentication with Identity Platform, a verified email, the modular web SDK (v9.19.1 or later), and Firebase Admin Node SDK v11.6.0 or later. Enrollment uses a generated TOTP secret plus a verification code; sign-in resolves `auth/multi-factor-auth-required` with the TOTP assertion. The server must only treat a session as MFA-verified when the verified Firebase session claims include `sign_in_second_factor: "totp"`.
  - https://firebase.google.com/docs/auth/web/totp-mfa
- **Enumeration and signup abuse:** Google recommends keeping email-enumeration protection enabled. Newer projects have it enabled by default; older ones should be checked in Authentication Settings. Google also recommends App Check and/or reCAPTCHA for signup abuse mitigation.
  - https://docs.cloud.google.com/identity-platform/docs/admin/email-enumeration-protection
- **App Check:** The official web guide supports reCAPTCHA v3 and recommends reCAPTCHA Enterprise for new integrations. This app's Express API fails closed on missing/invalid App Check tokens in production (and can be enabled in staging with `FIREBASE_APP_CHECK_REQUIRED=true`). Provider-side enforcement for Firebase Authentication is a separate console setting; monitor legitimate traffic before enabling it. Do not use or expose a production debug token.
  - https://firebase.google.com/docs/app-check/web/recaptcha-provider
- **Firebase Auth authorized domains:** Identity Platform's project config API exposes `authorizedDomains`; its `updateConfig` method accepts an `updateMask`, allowing only that field to be patched while preserving the rest of the config. The preview hostname was appended and read back with `updateMask=authorizedDomains`.
  - https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/projects/getConfig
  - https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/projects/updateConfig
- **reCAPTCHA key domains:** The website-key guide documents domain restrictions on website keys. This is separate from Firebase Authentication's Authorized Domains. The exact preview hostname has now been added to the reCAPTCHA key allowlist, but App Check token issuance still needs a successful retry after provider throttling.
  - https://docs.cloud.google.com/recaptcha/docs/create-key-website
- **Web auth SDK / emulator:** Firebase's modular SDK supports email/password signup and sign-in; its documentation recommends the Firebase Local Emulator Suite for prototyping and auth tests without touching live project data.
  - https://firebase.google.com/docs/auth/web/start
- **Federated email verification:** Firebase exposes `sendEmailVerification(user)` for the currently authenticated Firebase user. For a Google identity whose Firebase `emailVerified` flag is false, the client requests this verification email, ends the temporary client session, and still requires a fresh sign-in after verification; the server-side `email_verified` check is unchanged. Google documents that it is authoritative for Gmail addresses and for verified Google Workspace identities, but recommends an additional challenge for third-party addresses when it is not authoritative.
  - https://firebase.google.com/docs/auth/web/manage-users#send_a_user_a_verification_email
  - https://developers.google.com/identity/gsi/web/guides/verify-google-id-token

## Provider decisions and prerequisites

1. Confirm the configured Firebase / Identity Platform project is an isolated staging project; do not use real accounts or a live domain until the owner verifies the environment boundary.
2. Enable email/password and Google sign-in, require verified email, enable TOTP MFA, and keep email-enumeration protection enabled. TOTP is available to guardians and required for administrators.
3. To satisfy the product requirement that Google and password providers remain separate identities, select the Identity Platform policy that allows multiple accounts per email and do not implement client account-linking calls. Verify the current console wording and duplicate-email behavior before enabling real accounts.
4. Register only the staging preview and staging app origins in Google/Firebase. Firebase Authentication's Authorized Domains and the reCAPTCHA v3 website-key restriction now both include the exact preview host. Google OAuth client settings remain a separate check.
5. Register staging with App Check, observe metrics, then enable Authentication enforcement. Do not use a production App Check debug token.
6. Keep the Firebase service-account private key in the protected WebDev secret store. The browser configuration/API key and reCAPTCHA site key are public identifiers but should still be set as the named WebDev environment variables; no value belongs in source control or chat.
